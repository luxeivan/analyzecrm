# CRM Analyzer для Битрикс24 — описание сервиса

Документ описывает, что делает сервис, из чего он состоит, какие ресурсы потребляет и какие
затраты создаёт при эксплуатации. Он подготовлен как основа для оценки стоимости продажи
(лицензии / подписки / внедрения), поэтому все измеримые величины приведены фактическими —
снятыми с работающей прод-инсталляции.

Прод-инсталляция: `https://analyzecrm.luxeivan.ru` (данные реального портала Битрикс24).

---

## 1. Что это в одном абзаце

CRM Analyzer — надстройка над облачным Битрикс24, которая выгружает всю CRM (компании, контакты,
сделки, лиды) в собственное хранилище с векторными представлениями записей и даёт поверх этого
аналитику, семантический поиск, отчёт по дублям, поиск похожих клиентов, граф связей и
LLM-ассистента, который отвечает на вопросы по данным компании и формирует выжимку по клиенту.
Битрикс24 остаётся системой ввода данных, сервис становится «аналитическим слоем» поверх него
и не требует изменения привычек менеджеров.

---

## 2. Какую задачу решает

| Проблема в Битрикс24 | Что делает сервис |
|---|---|
| Стандартные отчёты не отвечают на вопросы «сколько реально клиентов», «какое качество базы», «где дубли» | Сквозной дашборд + страница аналитики: покрытие полей, дубли, конверсия, выручка, источники, динамика по периодам |
| Поиск ищет по названию/телефону, не понимает смысл | Семантический поиск по смыслу («производство мебели для офисов») + полнотекстовый поиск по **всем** полям, включая пользовательские `UF_*` |
| Дубли в базе никто не видит: клиент заведён 3–5 раз, сделки размазаны | Отчёт по дублям: пары с оценкой похожести (0–1), готовые группы дублей (union-find), сравнение карточек бок о бок |
| Непонятно, на кого похожи лучшие клиенты, чтобы искать таких же | «Потенциальные клиенты»: центроид профиля покупателей → список компаний, похожих на идеального клиента |
| Руководителю нужна выжимка по клиенту перед звонком | JSON-выжимка клиента для LLM + Markdown-резюме: профиль, кастомные поля, контакты, сделки, метрики, качество данных |
| Вопросы вида «кто наши крупнейшие клиенты и что с ними не так» требуют выгрузки в Excel | RAG-ассистент: вопрос → поиск по данным → ответ со ссылками на источники |
| Кастомные поля (`UF_*`) видны как ID справочников | Серверная расшифровка `enumeration`, статусов, источников — человеку показываются значения |

## 3. Функциональные модули

### 3.1 Интеграция и синхронизация (ETL)

- Работает через **входящий вебхук** Битрикс24 (`crm.company.list`, `crm.contact.list`,
  `crm.deal.list`, `crm.lead.list`), права только `crm`.
- Выгрузка **потоковая**: страница API = батч = транзакция upsert. Записи не накапливаются в памяти,
  поэтому объём базы ограничен только диском.
- **Keyset-пагинация** (`filter {>ID}` + `ORDER BY ID ASC`) вместо `OFFSET`: не теряет и не дублирует
  записи при параллельной работе менеджеров в CRM.
- Соблюдение лимитов портала: 50 записей на запрос, пауза между страницами (настраивается),
  retry с backoff на 429/5xx/сетевые ошибки, таймаут 55 с.
- **Инкрементальная синхронизация**: курсор (`last_id`) и статус в таблице `sync_state`; после
  остановки выгрузка продолжается с того же места.
- **Дельта по `DATE_MODIFY`**: после инкремента догружаются изменённые записи (окно перекрытия настраивается).
- **Сверка удалённых**: пакетная проверка ID (`50×50`) → записи, удалённые в CRM, помечаются/удаляются,
  аудит пишется в `deleted_records`.
- **Планировщик в API**: каждые N минут дельта, раз в N дней сверка удалённых; авто-повтор
  при ошибках (до 10 попыток) без участия человека.
- **Ручное управление из UI**: старт / пауза / продолжение / стоп, прогресс по каждой сущности
  (обработано записей, текущая страница, ETA). Пауза и стоп кооперативные — текущая страница
  всегда дописывается вместе с курсором.
- Сценарии запуска: кнопка в интерфейсе, CLI, cron/планировщик.

### 3.2 Хранилище и модель данных

PostgreSQL 16 + `pgvector` + `pg_trgm`.

- Нормализованные таблицы (`companies`, `contacts`, `deals`, `leads`) + **полный ответ API в `raw JSONB`**:
  ничего не теряется, любое новое поле можно поднять без перевыгрузки.
- Метаданные: `bitrix_fields` (все поля, включая `UF_*`, флаги множественности и элементы справочников),
  `bitrix_enum` (расшифровка `enumeration`), `crm_status` (источники, стадии, семантика S/F).
- `search_text` собирается рекурсивно из всех скалярных значений записи → GIN-индекс `pg_trgm`,
  поиск работает по любым полям.
- `embedding vector(1536)` + HNSW-индексы (`vector_cosine_ops`) для семантики и дублей.
- Служебные таблицы: `sync_state`, `service_state`, `deleted_records`, `duplicate_pairs`, `users`.

### 3.3 Аналитика

- **Дашборд**: KPI (компании, контакты, сделки, лиды, выручка, конверсия), качество данных,
  сегменты по отрасли или по любому полю-справочнику (`?segment=UF_CRM_...`), источники, города,
  стадии сделок и лидов, динамика по месяцам.
- **Страница «Аналитика»**: покрытие ключевых полей (телефон, e-mail, компания, отрасль, регион),
  выручка и win rate, разбивка по годам, топ клиентов, рекомендации по чистке базы.
  Фильтр периода (месяц/квартал/год/произвольный): сделки по дате начала, лиды по дате создания;
  качество данных всегда считается по всей базе (чтобы не путать срез с состоянием базы).
- **LLM-инсайты**: 5–7 выводов по данным портала, Markdown-рендер, стоимость запроса в рублях
  показывается пользователю, результат сохраняется локально.

### 3.4 Поиск (полнотекстовый и семантический)

- **Полнотекстовый**: `q` по названию и `search_text` (все поля, включая `UF_*`), ILIKE + GIN `pg_trgm`.
- **Семантический** (`/api/search/semantic`): запрос → эмбеддинг → HNSW → записи с оценкой близости.
  Работает по компаниям, контактам, сделкам, лидам.
- **Похожие записи**: блок «Похожие» на каждой карточке (`/api/similar/:entity/:id`).
- **Дубли** (см. 3.5) — отдельный сценарий с настраиваемым порогом.

### 3.5 Дубли

- Расчёт по всем записям сразу (не выборка): эмбеддинги → пары с косинусной близостью выше порога,
  батчи по 5 000, прогресс в `service_state`.
- Хранится таблица `duplicate_pairs` → отчёты строятся мгновенно, без пересчёта.
- Выдача: **пары** (A ↔ B, оценка), **группы** (union-find: «один клиент — N карточек»),
  точные группы, сводка по сущностям.
- **Сравнение**: Drawer с карточками всех записей группы в один ряд (горизонтальная прокрутка),
  сделками по каждой записи (количество, сумма, выигранные, топ-5).
- Факт с прод-базы: компании при пороге 0.9 — **2 140 групп / 5 825 записей, крупнейшая группа 29 карточек**,
  при 0.999 — 277 групп / 692 записи; контакты — 6 089 пар.

### 3.6 Потенциальные клиенты (look-alike)

Центроид эмбеддингов топ-N выигранных клиентов → ближайшие компании, исключая уже купивших.
К каждой строке — «похожа на» (какой клиент ближайший и с какой оценкой). Явно отделено от дублей:
это не «одна и та же компания», а «такой же профиль».

### 3.7 LLM-возможности

Провайдер настраивается (Polza.ai / любой OpenAI-совместимый), модель из `.env`.

| Сценарий | Что происходит | Измерено на проде |
|---|---|---|
| Инсайты по порталу | агрегаты → LLM → 5–7 выводов | ~3 930 токенов, **0.40 ₽** за запрос |
| Выжимка клиента | профиль + контакты + сделки + метрики + качество данных → JSON/Markdown | ~1–2 тыс. токенов |
| RAG-ассистент (`/api/ai/ask`) | вопрос → семантика (6 компаний, 5 сделок, 4 лида) → ответ со ссылками | 1 045 токенов, **0.078 ₽** за вопрос |

Стоимость каждого вызова возвращается в ответе (`usage.costRub`), то есть расходы на LLM
прозрачны и тарифицируемы.

### 3.8 Товары и анализ продаж

Каталог Битрикса (46 494 позиции, 1 003 раздела, иерархия 4+ уровней) и **состав каждой сделки**
(строки товаров: цена, количество, скидка, налог, единица измерения) выгружаются в собственные таблицы.

- **Рейтинг товаров**: сортировка по выручке, количеству, числу сделок или компаний-покупателей;
  фильтры по категории (с подкатегориями), периоду, «только проданные», переключатель
  «успешные сделки / все сделки».
- **Топ категорий** со свёрткой по дереву разделов: категория = она сама + все подкатегории.
- **Отчёт по товару** (`/products/:id`): KPI (выручка, количество, сделки, компании, скидки,
  первая/последняя продажа), график динамики по месяцам/кварталам/годам,
  **таблица компаний-покупателей** (выручка, количество, сделки и число выигранных, контакты,
  первая и последняя покупка, город, отрасль) с переходом в карточку компании,
  список последних сделок с этим товаром, выгрузка компаний в CSV.
- **Карточка компании** — блок «Что покупала компания» (топ товаров по выручке с переходом в отчёт).
- **Карточка сделки** — состав товаров с суммами и итогами.

Это закрывает вопрос «какой товар продаётся лучше, кому и когда» без выгрузок в Excel.

### 3.9 Граф связей

Компания → контакты → сделки и лиды (`react-force-graph-2d`), обзорный граф по топ-компаниям.
Подписи появляются при приближении, контейнер адаптируется через `ResizeObserver`.

### 3.10 Карточки сущностей

Компания / контакт / сделка / лид: расшифрованные поля (включая все `UF_*`), агрегаты по сделкам
(количество, сумма, выигранные, открытые), «Создана» и даты изменения, вложенные коллекции
с ограничением (200–500 записей), кнопка «JSON для LLM», блок похожих записей.

### 3.11 Администрирование и доступ

- JWT-аутентификация (HS256, без внешних зависимостей), пароли — scrypt-хэши.
- Роли: **admin** (всё) и **user** (только просмотр: без админки, синхронизации, настроек, пользователей).
- CRUD пользователей, защита системного администратора (нельзя удалить, понизить, отключить).
- Страница «Админка»: состояние синхронизации, прогресс векторизации, таблица векторов
  (записей / с эмбеддингом / актуальных / HNSW-индекс), размер БД, версия PostgreSQL,
  удалённые записи, последняя сверка, кнопки «Векторизация» и «Сверка удалённых», список настроек.
- Светлая и тёмная темы (включая страницу входа), адаптивная вёрстка.

## 4. Архитектура и объём кода

```
Битрикс24 (облако)
      │  REST, входящий вебхук, 50 записей/запрос
      ▼
  ETL (Node.js)  ──►  PostgreSQL 16 + pgvector  ──►  API (Express)  ──►  React SPA
  • потоковые батчи      • raw JSONB                    • фильтры          • Ant Design 5
  • keyset-курсоры       • поиск pg_trgm                • расшифровка      • Recharts
  • дельта/reconcile     • эмбеддинги HNSW              • граф, агрегаты   • граф (force-graph)
  • планировщик          • users, sync_state            • LLM/эмбеддинги
      │
      └──► LLM-провайдер (Polza.ai / OpenAI-совместимый): чат + text-embedding-3-small (1536)
```

| Компонент | Технологии | Объём |
|---|---|---|
| Backend (ETL + API) | Node.js 20, ESM, express, pg, axios | ~5 700 строк JS, 33 файла |
| Frontend | React 18, TypeScript, Vite, Ant Design 5, Recharts, react-force-graph-2d | ~6 400 строк TS/TSX, 32 файла |
| Инфраструктура | Docker Compose, nginx, PostgreSQL+pgvector | compose (dev + prod), Dockerfile'ы, nginx.conf |
| Документация и утилиты | Markdown, Python (PDF-отчёт) | ~600 строк |

Всего в репозитории ~20 000 строк, из них ~12 100 — прикладной код.

Развёртывание: 3 контейнера (`db`, `api`, `web`) + опциональный `embed` (векторизация) + `adminer`.
Образы: API — 52 МБ, web — 22 МБ.

## 6. Требования к окружению

- Linux-сервер (или Docker Desktop), **4 vCPU / 8 ГБ RAM / 100 ГБ SSD** — с запасом на 500 тыс. записей.
  Минимум для пилота: 2 vCPU / 4 ГБ / 50 ГБ.
- Docker + Docker Compose.
- PostgreSQL 16 с `pgvector` (входит в образ) — отдельная установка не нужна.
- HTTPS: nginx + Let's Encrypt (или Caddy).
- Доступы: входящий вебхук Битрикс24 с правами `crm`; ключ LLM-провайдера (опционально — без него
  приложение работает, ИИ-функции отключаются с подсказкой).
- Ничего не устанавливается на стороне Битрикс24 и в браузерах пользователей.

4. Настройка под поля конкретного портала (регион, сегменты, справочники).
5. Учётные записи с ролями (администраторы / наблюдатели).
6. Регламент: ежедневные бэкапы, автосинхронизация, обновление.
7. Обучение пользователей (интерфейс + чтение аналитики).

Не входит (обсуждается отдельно): доработка под нестандартные процессы, интеграции с 1С/телефонией,
мобильное приложение, SLA 24/7, миграция исторических данных из других CRM.

## 9. Ограничения (важно проговорить при продаже)

- **Один портал на инсталляцию** (`BITRIX_WEBHOOK_URL`), без OAuth и без мультитенантности:
  для нескольких клиентов — отдельные контейнеры/базы (архитектурно просто, но требует автоматизации выставления).
- **Нет real-time**: изменения подтягиваются по расписанию (по умолчанию 15 минут), вебхуки не используются.
- **Удаления** в CRM отслеживаются периодической сверкой (раз в 7 дней по умолчанию), а не мгновенно.
- **Нет биллинга/подписок** — тарификация пока вне сервиса.
- Тяжёлая аналитика на больших объёмах: `/analytics/overview` ~10 с (кэш/предагрегация — очевидная точка роста).
- Дубли и связывание контактов с компаниями не исправляются автоматически: сервис **показывает**,
  решение за человеком (это осознанно — автоматическая склейка в CRM опасна).
- Часть полей (`utm`, отдельные `iblock`-справочники) показывается ID.
- «Регион» — эвристика; при наличии настоящего `UF_*` настраивается за минуту.
- Внешний контур без авторизации не публикуется: сервис рассчитан на внутренний контур/закрытый доступ.

## 10. Как это оценивать в деньгах

### 10.1 Ориентиры ценности для клиента

Считаются по данным клиента после первого прогона (сервис даёт цифры сам):

| Метрика | Как получить |
|---|---|
| Число дублей и «склеенных» клиентов | Страница «Дубли»: группы, записи, крупнейшие группы |
| Какие товары продаются лучше и кому | Страница «Товары»: рейтинг по выручке, топ категорий |
| Кто покупал конкретный товар и когда | Отчёт по товару: динамика + таблица компаний с суммами и датами покупок |
| Доля записей с телефоном/e-mail/отраслью/регионом | Страница «Аналитика», блок качества данных |
| Разбросанные сделки одного клиента | Группы дублей + сумма сделок по каждой карточке |
| Время на подготовку выжимки по клиенту | До/после: 20–30 мин вручную против секунд |
| Время на «а кто наши лучшие клиенты и кто на них похож» | Раньше выгрузка + Excel, теперь одна страница |

### 10.2 Модели продажи

| Модель | Что продаётся | Когда уместна |
|---|---|---|
| **Self-hosted лицензия** | Код + развёртывание на сервере клиента, поддержка отдельно | Крупный клиент, требования к данным (данные не покидают контур) |
| **Подписка (SaaS)** | Доступ к инсталляции в вашем облаке, ежемесячная оплата | Средний бизнес, быстрый старт |
| **Внедрение + подписка** | Разовая настройка (2.5–4 дня) + ежемесячная поддержка/ИИ-расходы | Наиболее реалистичный вариант для Битрикс24-интегратора |
| **White-label для интегратора** | Сервис под брендом партнёра (Битрикс24-интеграторы, маркетинговые агентства) | Продажа через партнёрскую сеть |

### 10.3 Формула цены (для расчёта, не готовый прайс)

```
Цена_внедрения   = дни_внедрения × ставка_дня + лицензия
Цена_подписки/мес = (инфраструктура + LLM + поддержка) × маржа
                    + ценность_данных (кол-во записей / дублей — «тариф по объёму»)
```

Практические «якоря» для обсуждения с клиентом:
- экономия времени руководителя/аналитика: 4–10 ч/мес → при ставке 2 000–4 000 ₽/ч это 8–40 тыс. ₽/мес;
- найденные дубли: каждая «склеенная» карточка — это восстановленная история сделок и корректная аналитика;
- отказ от ручных Excel-выгрузок и сводок (обычно 1–2 дня в месяц работы аналитика).

### 10.4 Тарифная сетка (предложение структуры)

| Тариф | Объём базы | Функции | Ориентир |
|---|---|---|---|
| **Старт** | до 50 тыс. записей | дашборд, аналитика, поиск, карточки, граф | вход в продукт |
| **Бизнес** | до 300 тыс. записей | + семантика, дубли, look-alike, админка | основная продажа |
| **Корпоративный** | без ограничений, self-hosted | + LLM-инсайты, RAG-ассистент, роли, приоритетная поддержка | крупные порталы |
| **Партнёрский** | — | white-label, N инсталляций, обучение | интеграторы |

## 11. Готовность к продаже: что есть и чего нет

Готово и проверено на реальных данных (426 тыс. записей):

- полный цикл ETL с возобновлением, дельтой, сверкой удалённых и планировщиком;
- 4 сущности CRM, расшифровка кастомных полей, поиск по любым полям;
- семантика (эмбеддинги + HNSW), похожие записи, дубли с группами и сравнением, look-alike;
- LLM: инсайты, выжимка клиента, RAG-ассистент с источниками и учётом стоимости;
- роли, JWT, CRUD пользователей, защита системного администратора;
- админка с прогрессом фоновых задач; прод-стек в Docker, HTTPS, ежедневные бэкапы.

Требуется доработать до «продуктовой» продажи (оценка по объёму работ):

| Задача | Зачем | Оценка |
|---|---|---|
| Мультитенантность + автоматизация развёртывания | продавать подписку без ручной работы | 2–3 недели |
| Биллинг/подписки и лимиты по тарифам | монетизация | 1–2 недели |
| Предагрегация тяжёлой аналитики | `/analytics` 10 с → <1 с на больших базах | 3–5 дней |
| Вебхуки Битрикс24 (real-time) | сделки/лиды почти без задержки | 3–5 дней |
| Экспорт отчётов (Excel/PDF), планировщик рассылок | ожидаемая функция у ЛПР | 3–5 дней |
| Онбординг-мастер (вебхук → выгрузка → настройка полей) | сократить внедрение до часов | 1 неделя |
| Мониторинг, алерты, SLA-регламент | продажа корпоративным клиентам | 3–5 дней |

## 12. Краткое резюме для переговоров

- Продукт **рабочий и проверенный** на большой реальной базе: 51 тыс. компаний, 103 тыс. контактов,
  83 тыс. сделок, 188 тыс. лидов; 4.7 ГБ; ответы API — миллисекунды, семантика — 1.4 с.
- Себестоимость эксплуатации — **2–5 тыс. ₽/мес** на клиента при 100 ИИ-вопросах в день.
- Внедрение — **2.5–4 дня**, дальше клиент живёт на автосинхронизации.
- Сильные стороны, которые дорого воспроизвести: связка «ETL с возобновлением + эмбеддинги + дубли
  группами + RAG по своим данным» в одном закрытом контуре, без передачи данных третьим лицам.
- Слабые стороны, которые нужно закрыть до масштабной продажи: мультитенантность, биллинг,
  скорость тяжёлой аналитики, real-time, экспорт отчётов.
